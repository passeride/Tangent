## Problem and users

What does the person want to accomplish? What do they already know, and which
constraints matter (piano, mouse, touch, screen size, sound or permissions)?

## Scope

What will this study decide, and what is outside it?

## Flow and states

Describe the main path plus loading, empty, error, unavailable-capability and
interrupted states. Include recovery actions. Explain focus and input ownership
where piano shortcuts and text entry can overlap.

## Sketches and variants

Link files in `sketches/`. For each variant, state what is being compared, the
viewport, input assumptions and which questions remain open. Supply a text
summary so the meaning does not depend only on an image.

## Accessibility and feedback

Cover scaling, contrast, non-color feedback, keyboard/focus behavior, reduced
motion and optional audio cues as relevant.

## Validation

What interaction or observation would show this design works? Name the target
viewport/device and distinguish a mockup review from a running-app test.

## Outcome

Not decided. Record the selected direction, tradeoffs and follow-up after review.
A selected sketch is not evidence that the feature has been implemented.

## Sources and assets

List original work, external references, authors, license/permission and any AI
assistance. Add reusable files to the asset register before implementation uses
them. Do not attach material copied from excluded source projects.
